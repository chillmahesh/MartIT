## 2. ORDER LIFECYCLE SUMMARY
1. Creation & Reservation:
   - Route `server/src/routes/orders.js` (`handleCreateOrder`, lines 270-362) calls RPC `create_order_atomic`.
   - RPC reserves inventory rows in `inventory_reservations` with `status = 'HELD'`, decrements `products.stock_quantity`, creates a fee reservation in `platform_fee_reservations`, and sets `orders.payment_status = 'PENDING'`, `orders.status = 'PENDING'`, and `orders.payment_window_expires_at = NOW() + INTERVAL '2 minutes'`.
2. QR & Payment Attempt:
   - Customer UI (`src/components/payment/PaymentQr.jsx`, lines 31-48; `src/utils/upi.js`, line 14) constructs a raw static NPCI UPI URI (`upi://pay?pa=...&am=...&tr=ord_...`).
   - Purely client-side string generation; no transaction intent or session is registered with any payment gateway or bank.
3. Webhook Ingestion:
   - Notification arrives at `server/src/routes/webhooks.js` (`handleMakePaymentWebhook`, lines 212-420) from Make.com.
   - (Clarification: Make.com operates outbound via MAKE_VERIFICATION_WEBHOOK_URL; no incoming webhook secret exists).
   - Ingested record inserted into `payment_records` as `status = 'PROCESSING'`, `verification_source = 'MAKE_WEBHOOK_INGESTION'`.
   - Verification pipeline invokes `verifyWithAuthoritativePaymentGateway`. In production, no gateway is wired, returning `verified: false`. Webhook halts without confirming order.
4. Polling & Automated Expiry:
   - Frontend polls `server/src/routes/orders.js` (`handleCheckPayment`, lines 388-510).
   - Route checks `payment_records` for `status = 'PAID'` and `verification_source = 'AUTHORITATIVE_GATEWAY'`.
   - Finding none, it returns `inconclusive` until `payment_window_expires_at` is reached.
   - Once expired, `executeAtomicPaymentExpiry` invokes RPC `expire_order_payment`, setting `orders.payment_status = 'EXPIRED'`, `orders.status = 'CANCELLED'`, reverting inventory reservations (`status = 'RELEASED'`), and restoring stock.

## 3. CONFIRMED BY CODE
1. Authoritative Verification Dead End (Fails Closed):
   - Location: `server/src/routes/webhooks.js` lines 117-135, 391-409; `server/src/routes/orders.js` lines 434-456.
   - Finding: Default gateway verifier returns `{ verified: false, reason: 'NO_AUTHORITATIVE_GATEWAY_INTEGRATION' }`. The webhook does not call `executeAtomicPaymentVerification()`. Polling endpoint cannot find an `AUTHORITATIVE_GATEWAY` record.
   - Consequence: Every legitimate live customer payment is stuck in `PROCESSING`, leaving orders `PENDING` until 2-minute timer forces order cancellation and stock release.
2. Late Webhook Notification Telemetry Blackout:
   - Location: `server/src/routes/webhooks.js` lines 266-273, lines 283-290.
   - Finding: If an order reaches terminal state (`PAID`, `CANCELLED`, `REFUNDED`) or if `payment_window_expires_at < new Date()`, webhook returns HTTP 409 or HTTP 400 immediately.
   - Evidence: Ingestion into `payment_records` occurs at line 312, strictly after lines 270 and 285.
   - Consequence: Customer payments arriving after 2 minutes or after cancellation are rejected at HTTP boundary with zero database record, UTR log, or audit trail in `payment_records`.
3. Database Concurrency Serialization & Locks:
   - Location: `supabase/migrations/20261021000001_seed_canonical_campus_locations_and_atomic_orders.sql` lines 275 and 325.
   - Finding: Both `mark_platform_fee_paid` and `expire_order_payment` execute `SELECT payment_status, status FROM public.orders WHERE id = p_order_id FOR UPDATE`.
   - Consequence: Race conditions between verification and expiration are strictly serialized at the PostgreSQL row level. The first transaction wins; the second encounters updated status and throws `CANNOT_VERIFY_TERMINAL_PAYMENT` or `CANNOT_EXPIRE_PAID_ORDER`.
4. Payment Record Amount Integrity Trigger:
   - Location: `supabase/migrations/20261022150000_require_authoritative_payment_verification.sql` lines 30-58.
   - Finding: PostgreSQL trigger `trg_verify_payment_record_amount` asserts `NEW.amount = v_total_payable`.
   - Consequence: Partial payments or tampering cannot transition or persist as valid payment records for the order.
5. RPC and Table Authorization:
   - Location: `supabase/migrations/20261022160000_restrict_payment_transition_rpc.sql` and `20261010000003_row_level_security.sql`.
   - Finding: `mark_platform_fee_paid` execution revoked from `PUBLIC`, `anon`, and `authenticated`; granted only to `service_role`. `payment_records` table has RLS enabled with only customer SELECT permitted; insert/update restricted to `service_role`.

2. Verified Behaviors:
   - Pluggable gateway verifier: When a custom verifier resolves `{ verified: true }`, webhook marks order `PAID` and `CONFIRMED` and stores evidence.
   - Evidence write failure: When persisting evidence fails, webhook aborts verification and keeps order `PENDING`.
   - Non-boolean return value: Truthy non-boolean values fail closed and leave order `PENDING`.
   - Gateway rejection: When gateway returns `{ verified: false }`, order remains `PENDING`.
   - Idempotency on paid orders: Re-delivered webhooks for already-paid orders return HTTP 200 with idempotent event without duplicate state mutations.
3. Critical Caveat:
   - All passing tests use an in-memory mocked `customGatewayVerifier`. No tests run against real network endpoints, real bank APIs, or live Paytm servers.

## 7. UNKNOWN / REQUIRES INVESTIGATION
1. Order Reinstatement Safety:
   - An expired order cannot be safely reinstated automatically. Once an order expires, its inventory reservations (`inventory_reservations`) are deleted or marked `RELEASED`, returning stock to general availability. Reinstating without re-checking stock could lead to negative inventory or unfulfillable orders.
2. Transaction Boundary Latencies:
   - If an external gateway HTTP call is made while holding database connections or long-lived locks, connection pool exhaustion could occur. External gateway calls must execute outside the PostgreSQL transaction boundary.
3. Admin Reconciliation Authorization:
   - Administrative reconciliation is not secure by default. Database RLS, role checks, and dual-custody audit logs must be designed and verified before allowing manual payment overrides.
